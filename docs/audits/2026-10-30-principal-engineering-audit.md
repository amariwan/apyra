# Apyra principal engineering audit

**Snapshot:** 2026-10-30 baseline, with follow-up findings and verification through 2026-10-31. This audit covers confirmed issues found and fixes implemented during the local review. It is not exhaustive security coverage; hosted CI status is specific to the draft PR and commit recorded below, not the dirty local worktree or `main`.

**Disposition:** 87 confirmed findings are listed below. 86 have implemented remediations in the local worktree; the P0 Channels import fix also passes hosted CI in draft PR #2. Cookie-authenticated CSRF remains opt-in in the library and is now wired into the explicit `apyra new --template cookie-auth` starter; the default minimal starter remains unchanged. Residual operational, application-boundary, and scan-coverage limitations are listed separately.

| High | **JWT validation configuration:** `packages/auth/src/apyra/auth/jwt.py` and `tokens.py`. | Configuring issuer/audience verification without corresponding expected values could silently weaken validation; family revocation also needed to invalidate existing access credentials. | High | **TokenService accepted access JWTs without expiry:** `packages/auth/src/apyra/auth/tokens.py`. | Unlike `JWTAuthenticator`, the token service did not require `exp` (or `sub`/`iat`), so a correctly signed token without expiration could remain valid indefinitely. | Require `sub`, `iat`, and `exp` in the shared token decode path. ## Consumer migration notes

These notes make the affected contracts reviewable; they do not approve a breaking release or select its version.

- **JWT configuration:** provide `AUTH_ISSUER` and `AUTH_AUDIENCE` when the corresponding verification flags are enabled, keep `AUTH_VERIFY_EXP=true`, use HTTPS for JWKS, and implement both synchronous `is_revoked(jti)` and `is_family_revoked(family_id)` methods in custom revocation stores.
- **OIDC/OAuth:** token providers should return a non-empty `token_type`; missing values temporarily fall back to `Bearer` with `DeprecationWarning` and must be fixed before the next major `apyra-auth` release. Pass `userinfo()` the `sub` from an ID token the application has cryptographically validated; pass standard OAuth fields through named arguments, not `extra_params`; use HTTPS discovery, JWKS, token, and revocation endpoints. The verified-subject requirement remains immediate for security.
- **Events:** instantiate `InMemoryEventBus` or a complete concrete adapter. Downstream `EventBus` subclasses should implement both `publish()` and `subscribe()`; incomplete subclasses warn now and abstract enforcement is deferred until no earlier than the next major `apyra-events` release.
- **Memcached and database cursors:** call Memcached `clear()` only on a dedicated server and only after setting `CACHE_MEMCACHED_ALLOW_SERVER_FLUSH=true`; expire existing scalar-format cursors during rollout and have clients restart pagination after deployment.
- **HTTP integrations:** move remote AI and S3 endpoints to HTTPS. `AIClient` permits a trusted private non-loopback HTTP endpoint only with `allow_insecure_http=True`; this sends any configured API key without transport encryption. OIDC/JWKS endpoints require HTTPS without an insecure override.
- **Defensive values:** mutations to sessions returned by `InMemorySessionStore.create()` or `.get()` no longer update stored state; persist changes through an application-owned update boundary because this store contract has no update method. `EmailMessage.headers` is immutable; construct a replacement message when headers change.
- **Cookie CSRF:** library behavior remains opt-in. New cookie-auth starters can use `apyra new <name> --template cookie-auth`, which requires `APYRA_CSRF_SECRET` (at least 32 UTF-8 bytes), sets a script-readable CSRF cookie with `Secure` enabled by default, and protects unsafe routes with a token bound to `access_token`. Origin validation and production cookie/auth-provider configuration remain application-owned. Set `APYRA_COOKIE_SECURE=false` only for local HTTP development.
- **Version decision:** use the approved per-surface deprecation period and defer removal to no earlier than the next major release of each affected package. No specific version, publishing, or release has been approved; security invariants remain enforced immediately.
